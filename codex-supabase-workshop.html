P01 — ตรวจโปรเจกต์และวางโครงสร้าง

ใช้เมื่อ: เริ่มก่อนสร้างตารางหรือเปลี่ยน stack

เปิดอ่านคำสั่งฉบับเต็ม
บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
สำรวจ package.json, scripts, routing, env, Auth, database integration และ deployment config โดยไม่เปิด secrets ออกมา
ทำ PROJECT-AUDIT.md บอกว่าอะไรมีแล้ว อะไรขาด และปัญหาใดกีดขวางการเปิดขาย
เสนอโครงสร้างตาม framework เดิม เช่น src/features/auth, media, admin, attempts และ src/lib/supabase, src/services, src/types รวม supabase/migrations, scripts/import, tests/security และ docs
ใช้ repository/service layer เฉพาะส่วนที่ช่วยแยกการอ่านข้อมูลออกจาก UI ไม่สร้าง abstraction ซ้อนโดยไม่จำเป็น
กำหนด error/loading/empty states และวิธีตั้ง env แยก local/staging/production
คง framework เดิมถ้าใช้งานได้ ถ้าจำเป็นต้องเปลี่ยนให้บอกเหตุผลและผลกระทบก่อนทำ
เริ่มแก้ส่วนที่เป็น local และย้อนกลับได้ พร้อมสรุปไฟล์ที่แก้

ตรวจว่าจบขั้นนี้แล้ว: มีแผนผังไฟล์และรายการ gap พร้อมคำสั่งรันจริง ไม่มีการเปลี่ยน production

P02 — ออกแบบตาราง Supabase

ใช้เมื่อ: หลังรู้โค้ดและ schema ปัจจุบัน

เปิดอ่านคำสั่งฉบับเต็ม
บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
ออกแบบ schema PostgreSQL ที่รองรับสมาชิก สิทธิ์ และสื่ออย่างเป็นระเบียบ สร้าง SCHEMA.md พร้อม ER diagram และ data dictionary
ตารางตั้งต้น:
profiles: id อ้าง auth.users, display_name, created_at, updated_at ไม่เก็บ password และไม่ให้แก้ role ในตารางนี้
user_roles: user_id, role (owner/admin/member) ใช้แหล่งที่สมาชิกแก้ไม่ได้ ระบุหนึ่งหรือหลาย role ให้ชัดและใช้สม่ำเสมอ
plans: id, code unique, name, status รุ่นแรกมี all_access แผนเดียว
entitlements: id, user_id, plan_id, status (pending/active/revoked), expires_at nullable, granted_by, created_at, updated_at, version มี unique(user_id,plan_id) หากเลือกหนึ่งสิทธิ์ต่อแผน
media_catalog: id, slug unique, title, category, kind, is_free, publication_status (draft/published/archived), content_version, created_at, updated_at
media_content: media_id FK, schema_version, payload jsonb ที่มีการ validate รุ่น schema แยกเนื้อหาเสียเงินออกจาก metadata
media_assets: id, media_id, storage_backend, object_path, mime_type, size_bytes, checksum, version ห้ามเก็บ signed URLs ถาวร
attempts: id, user_id, media_id, score, completed_at และ submission_key ป้องกัน submit ซ้ำ
audit_logs: actor_id, target_id, action, before/after ที่ไม่เก็บ secrets, created_at, request_id
import_jobs: id, created_by, status, progress, manifest_version, error_summary, created_at
เพิ่มตารางเชื่อม plan_media เมื่อมีความต้องการขายแยกชุดจริง รุ่นแรกไม่ต้องสร้างระบบแพ็กเกจเต็มรูปแบบ
อธิบาย foreign keys, unique/check constraints, timestamps แบบ timestamptz และ deletion behavior ของทุก FK
วาง indexes ตาม queries จริง เช่น user_id, plan_id, status, category, publication_status และ completed_at ไม่สร้าง index ทุก column
Expired เป็นสถานะที่คำนวณจาก expires_at กับเวลาฐานข้อมูล ไม่ต้องแก้ทุกแถวด้วย cron เพื่อให้หมดสิทธิ์
เลือกวิธี archive สื่อและเก็บ audit โดยไม่ cascade ลบประวัติสำคัญโดยไม่ตั้งใจ
เก็บข้อมูลเด็กเท่าที่จำเป็น ให้บัญชีผู้ปกครองเป็นเจ้าของผลกิจกรรม
ถ้ามี schema เดิม ให้ทำ mapping และ migration plan แทนการสร้างชื่อซ้ำหรือ drop tables

ตรวจว่าจบขั้นนี้แล้ว: SCHEMA.md ระบุความสัมพันธ์ ชนิดข้อมูล ข้อจำกัด และ query ที่ต้องรองรับ

P03 — สร้าง SQL migrations และ seed

ใช้เมื่อ: หลังตกลง schema จากชุด 02

เปิดอ่านคำสั่งฉบับเต็ม
บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้

งานรอบนี้:
สร้าง SQL migration files ตามลำดับ แยก schema/constraints, indexes, policies, functions และ test seed ให้ตรวจง่าย
ตรวจฐานเดิมก่อนใช้ CREATE/ALTER ไม่ใช้ IF NOT EXISTS เพื่อซ่อนความต่างของ schema โดยไม่มีการตรวจ
ทำ migrations แบบเพิ่มก่อนเปลี่ยนและลบ (expand/contract) เมื่อต้องรักษา app เวอร์ชันเดิม
แยก seed กิจกรรมตัวอย่างออกจากข้อมูล production ไม่ใส่ password, tokens หรือบัญชีจริง
ทำ dry-run หรือ review script ตาม CLI ปัจจุบัน ไม่รัน db push ไป production
สร้าง docs/MIGRATIONS.md อธิบายวิธี local apply, staging apply, review และ production rollout พร้อม backup ก่อนงานเสี่ยง
อธิบายว่า db reset ล้างและสร้างฐานใหม่ ใช้เฉพาะ local/test ที่ยอมทิ้งได้ ห้ามใช้ --linked หรือ --db-url กับ production
หากต้องใช้ local Supabase ให้บอก prerequisite ของ CLI/runtime ตามเอกสาร และให้ทางเลือก SQL Editor บน test project หากไม่พร้อม
ทดสอบ migrations กับฐานใหม่ และเส้นทาง upgrade จาก schema เดิมถ้ามี

ตรวจว่าจบขั้นนี้แล้ว: สร้างฐานทดสอบได้ซ้ำ และ upgrade ไม่ทำข้อมูลเดิมหายโดยไม่ตั้งใจ

P04 — สร้าง RLS และตารางสิทธิ์

ใช้เมื่อ: ก่อนให้ frontend อ่านข้อมูลจริง

เปิดอ่านคำสั่งฉบับเต็ม
บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
สร้าง access matrix ก่อนเขียน policies: anonymous, member pending, active member, revoked/expired, admin, owner
เปิด RLS และกำหนด grants ให้ครบทุกตารางที่ exposed ผ่าน API
สมาชิกอ่าน/แก้ display_name ของตนได้ แต่แก้ user_roles, entitlements หรือ publication flags ไม่ได้ ใช้ column grants หรือ function แบบ allowlist ถ้าตารางมีหลายชนิดข้อมูล
anonymous อ่านเฉพาะ metadata สาธารณะและกิจกรรมฟรีที่ published
สมาชิก active อ่าน paid content ที่ published และอยู่ในขอบเขตสิทธิ์ของตนได้ ตรวจ expires_at โดย now() ฝั่ง DB
member อ่าน/เขียน attempts ของตนตามข้อจำกัด แต่สวม user_id ผู้อื่นไม่ได้
audit_logs ให้ผู้มีสิทธิ์ดูตามหน้าที่ แต่ห้าม client แก้หรือลบ log
user_roles ตรวจจากตาราง trusted ฝั่ง DB ไม่เชื่อ user_metadata หรือ role ที่ส่งจาก browser
ถ้าต้องมี helper function ตรวจ role เพื่อเลี่ยง RLS recursion ให้อยู่ใน schema ที่เหมาะสม และออกแบบสิทธิ์เรียกแบบแคบ
ใช้ SECURITY INVOKER เป็นค่าเริ่มต้น SECURITY DEFINER เฉพาะที่จำเป็น พร้อม search_path ที่ปลอดภัยและ qualify ชื่อทุก object
ตรวจ views/functions ไม่ bypass policies โดยไม่ตั้งใจ และตรวจ endpoint ตรงไม่ใช่เฉพาะ UI
สร้าง tests สำหรับ read/write/delete และ self-escalation โดย session ผู้ใช้จริง ไม่ใช้ SQL Editor admin เป็นหลักฐานผ่าน

ตรวจว่าจบขั้นนี้แล้ว: ผู้ไม่มีสิทธิ์เรียก API ตรงแล้วไม่ได้ paid content หรือข้อมูลผู้อื่น

P05 — สร้างฟังก์ชันเปิด–ปิดสิทธิ์

งานรอบนี้:

ทุกคำขอตรวจ auth.uid()/session จริงและ role จากตาราง trusted ไม่รับ actor_id ที่ caller เลือกเอง
admin จัดสิทธิ์สื่อสมาชิกได้ owner จัด roles ได้ แยกสิทธิ์ตั้ง admin ออกจากสิทธิ์อนุมัติผู้ซื้อ

ถ้ามี serverless ต่อ Postgres โดยตรง ให้เลือก pooling/driver ตาม runtime และข้อจำกัด prepared statements ตาม docs ไม่ถือว่า Supabase browser SDK ใช้ TCP pool แบบเดียวกัน
งาน import/ประมวลผลยาวให้ batch/job ไม่ทำทั้งหมดใน request เดียว
ทำ monitoring สำหรับ latency p95, error rate, DB load, storage bandwidth และ quota
เตรียม load-test plan ตาม user concurrency และ activity patterns ไม่รันทดสอบ provider จนมี authorization
อธิบายจุดขยายและค่าใช้จ่าย ห้ามรับประกันว่า scale ได้ไร้ปัญหา หรือเสนอ Kubernetes โดยไม่มีเหตุผล
