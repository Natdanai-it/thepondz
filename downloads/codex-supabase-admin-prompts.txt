ขั้น 2: เลือกบริการและวางงบ | P01 01 ตรวจโปรเจกต์และวางโครงสร้าง
ใช้เมื่อ: เริ่มก่อนสร้างตารางหรือเปลี่ยน stack

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
สำรวจ package.json, scripts, routing, env, Auth, database integration และ deployment config โดยไม่เปิด secrets ออกมา
ทำ PROJECT-AUDIT.md บอกว่าอะไรมีแล้ว อะไรขาด และปัญหาใดกีดขวางการเปิดขาย
เสนอโครงสร้างตาม framework เดิม เช่น src/features/auth, media, admin, attempts และ src/lib/supabase, src/services, src/types รวม supabase/migrations, scripts/import, tests/security และ docs
ใช้ repository/service layer เฉพาะส่วนที่ช่วยแยกการอ่านข้อมูลออกจาก UI ไม่สร้าง abstraction ซ้อนโดยไม่จำเป็น
กำหนด error/loading/empty states และวิธีตั้ง env แยก local/staging/production
คง framework เดิมถ้าใช้งานได้ ถ้าจำเป็นต้องเปลี่ยนให้บอกเหตุผลและผลกระทบก่อนทำ
เริ่มแก้ส่วนที่เป็น local และย้อนกลับได้ พร้อมสรุปไฟล์ที่แก้

ตรวจผล: มีแผนผังไฟล์และรายการ gap พร้อมคำสั่งรันจริง ไม่มีการเปลี่ยน production


ขั้น 5: สร้างฐานข้อมูลและกฎสิทธิ์ | P02 02 ออกแบบตาราง Supabase
ใช้เมื่อ: หลังรู้โค้ดและ schema ปัจจุบัน

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
ออกแบบ schema PostgreSQL ที่รองรับสมาชิก สิทธิ์ และสื่ออย่างเป็นระเบียบ สร้าง SCHEMA.md พร้อม ER diagram และ data dictionary
ตารางตั้งต้น:
profiles: id อ้าง auth.users, display_name, created_at, updated_at ไม่เก็บ password และไม่ให้แก้ role ในตารางนี้
user_roles: user_id, role (owner/admin/member) ใช้แหล่งที่สมาชิกแก้ไม่ได้ ระบุหนึ่งหรือหลาย role ให้ชัดและใช้สม่ำเสมอ
plans: id, code unique, name, status รุ่นแรกมี all_access แผนเดียว
entitlements: id, user_id, plan_id, status (pending/active/revoked), expires_at nullable, granted_by, created_at, updated_at, version มี unique(user_id,plan_id) หากเลือกหนึ่งสิทธิ์ต่อแผน
media_catalog: id, slug unique, title, category, kind, is_free, publication_status (draft/published/archived), content_version, created_at, updated_at
media_content: media_id FK, schema_version, payload jsonb ที่มีการ validate รุ่น schema แยกเนื้อหาเสียเงินออกจาก metadata
media_assets: id, media_id, storage_backend, object_path, mime_type, size_bytes, checksum, version ห้ามเก็บ signed URLs ถาวร
attempts: id, user_id, media_id, score, completed_at และ submission_key ป้องกัน submit ซ้ำ
audit_logs: actor_id, target_id, action, before/after ที่ไม่เก็บ secrets, created_at, request_id
import_jobs: id, created_by, status, progress, manifest_version, error_summary, created_at
เพิ่มตารางเชื่อม plan_media เมื่อมีความต้องการขายแยกชุดจริง รุ่นแรกไม่ต้องสร้างระบบแพ็กเกจเต็มรูปแบบ
อธิบาย foreign keys, unique/check constraints, timestamps แบบ timestamptz และ deletion behavior ของทุก FK
วาง indexes ตาม queries จริง เช่น user_id, plan_id, status, category, publication_status และ completed_at ไม่สร้าง index ทุก column
Expired เป็นสถานะที่คำนวณจาก expires_at กับเวลาฐานข้อมูล ไม่ต้องแก้ทุกแถวด้วย cron เพื่อให้หมดสิทธิ์
เลือกวิธี archive สื่อและเก็บ audit โดยไม่ cascade ลบประวัติสำคัญโดยไม่ตั้งใจ
เก็บข้อมูลเด็กเท่าที่จำเป็น ให้บัญชีผู้ปกครองเป็นเจ้าของผลกิจกรรม
ถ้ามี schema เดิม ให้ทำ mapping และ migration plan แทนการสร้างชื่อซ้ำหรือ drop tables

ตรวจผล: SCHEMA.md ระบุความสัมพันธ์ ชนิดข้อมูล ข้อจำกัด และ query ที่ต้องรองรับ

ใช้เมื่อ: หลังตกลง schema จากชุด 02

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้

งานรอบนี้:
สร้าง SQL migration files ตามลำดับ แยก schema/constraints, indexes, policies, functions และ test seed ให้ตรวจง่าย
ตรวจฐานเดิมก่อนใช้ CREATE/ALTER ไม่ใช้ IF NOT EXISTS เพื่อซ่อนความต่างของ schema โดยไม่มีการตรวจ
ทำ migrations แบบเพิ่มก่อนเปลี่ยนและลบ (expand/contract) เมื่อต้องรักษา app เวอร์ชันเดิม
แยก seed กิจกรรมตัวอย่างออกจากข้อมูล production ไม่ใส่ password, tokens หรือบัญชีจริง
ทำ dry-run หรือ review script ตาม CLI ปัจจุบัน ไม่รัน db push ไป production
สร้าง docs/MIGRATIONS.md อธิบายวิธี local apply, staging apply, review และ production rollout พร้อม backup ก่อนงานเสี่ยง
อธิบายว่า db reset ล้างและสร้างฐานใหม่ ใช้เฉพาะ local/test ที่ยอมทิ้งได้ ห้ามใช้ --linked หรือ --db-url กับ production
หากต้องใช้ local Supabase ให้บอก prerequisite ของ CLI/runtime ตามเอกสาร และให้ทางเลือก SQL Editor บน test project หากไม่พร้อม
ทดสอบ migrations กับฐานใหม่ และเส้นทาง upgrade จาก schema เดิมถ้ามี

ตรวจผล: สร้างฐานทดสอบได้ซ้ำ และ upgrade ไม่ทำข้อมูลเดิมหายโดยไม่ตั้งใจ


ขั้น 5: สร้างฐานข้อมูลและกฎสิทธิ์ | P04 04 สร้าง RLS และตารางสิทธิ์
ใช้เมื่อ: ก่อนให้ frontend อ่านข้อมูลจริง

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
สร้าง access matrix ก่อนเขียน policies: anonymous, member pending, active member, revoked/expired, admin, owner
เปิด RLS และกำหนด grants ให้ครบทุกตารางที่ exposed ผ่าน API
สมาชิกอ่าน/แก้ display_name ของตนได้ แต่แก้ user_roles, entitlements หรือ publication flags ไม่ได้ ใช้ column grants หรือ function แบบ allowlist ถ้าตารางมีหลายชนิดข้อมูล
anonymous อ่านเฉพาะ metadata สาธารณะและกิจกรรมฟรีที่ published
สมาชิก active อ่าน paid content ที่ published และอยู่ในขอบเขตสิทธิ์ของตนได้ ตรวจ expires_at โดย now() ฝั่ง DB
member อ่าน/เขียน attempts ของตนตามข้อจำกัด แต่สวม user_id ผู้อื่นไม่ได้
audit_logs ให้ผู้มีสิทธิ์ดูตามหน้าที่ แต่ห้าม client แก้หรือลบ log
user_roles ตรวจจากตาราง trusted ฝั่ง DB ไม่เชื่อ user_metadata หรือ role ที่ส่งจาก browser
ถ้าต้องมี helper function ตรวจ role เพื่อเลี่ยง RLS recursion ให้อยู่ใน schema ที่เหมาะสม และออกแบบสิทธิ์เรียกแบบแคบ
ใช้ SECURITY INVOKER เป็นค่าเริ่มต้น SECURITY DEFINER เฉพาะที่จำเป็น พร้อม search_path ที่ปลอดภัยและ qualify ชื่อทุก object
ตรวจ views/functions ไม่ bypass policies โดยไม่ตั้งใจ และตรวจ endpoint ตรงไม่ใช่เฉพาะ UI
สร้าง tests สำหรับ read/write/delete และ self-escalation โดย session ผู้ใช้จริง ไม่ใช้ SQL Editor admin เป็นหลักฐานผ่าน

ตรวจผล: ผู้ไม่มีสิทธิ์เรียก API ตรงแล้วไม่ได้ paid content หรือข้อมูลผู้อื่น


ขั้น 5: สร้างฐานข้อมูลและกฎสิทธิ์ | P05 05 สร้างฟังก์ชันเปิด–ปิดสิทธิ์
ใช้เมื่อ: ใช้เป็นช่องทางเปลี่ยนสิทธิ์เพียงจุดเดียว

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
สร้าง RPC หรือ API ฝั่ง server สำหรับ grant_access, revoke_access และ set_expiry เลือกวิธีให้สอดคล้องกับโค้ดเดิม
ทุกคำขอตรวจ auth.uid()/session จริงและ role จากตาราง trusted ไม่รับ actor_id ที่ caller เลือกเอง
admin จัดสิทธิ์สื่อสมาชิกได้ owner จัด roles ได้ แยกสิทธิ์ตั้ง admin ออกจากสิทธิ์อนุมัติผู้ซื้อ
validate target user, plan, expires_at และ reason จำกัดความยาวข้อมูล
เปลี่ยน entitlement กับ append audit log ใน transaction เดียว ถ้า log ล้มเหลวให้การเปลี่ยนสิทธิ์ไม่สำเร็จ
ใช้ expected_version หรือการล็อกที่เหมาะสมป้องกัน admin สองคนเขียนทับโดยไม่รู้
รองรับ request_id/idempotency เพื่อกดซ้ำแล้วไม่สร้างผลซ้ำ
หากใช้ SECURITY DEFINER ให้ revoke EXECUTE จาก PUBLIC/anon และ grant เท่าที่ต้องใช้ พร้อมตรวจ role ภายในทุกครั้ง สมาชิกที่ล็อกอินอาจเรียก function ได้แต่ต้องถูกปฏิเสธถ้าไม่ใช่ admin
ระบบ role management ต้องป้องกันลบ/ลด owner คนสุดท้ายและ race condition โดยตรวจแบบ transactional
อย่าตรวจ admin จากอีเมลใน frontend และอย่าใช้ service_role ใน browser
ทำ test admin, owner, member และ unauthenticated รวมคำขอปลอมและ retry

ตรวจผล: สมาชิกเปิดสิทธิ์ตนเองไม่ได้ ทุกการเปลี่ยนมี audit ที่สัมพันธ์กัน


ขั้น 6: เชื่อมสมาชิกและหน้าเจ้าของ | P06 06 สร้าง Auth และ session flow
ใช้เมื่อ: หลัง policies และ functions พร้อม

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
เชื่อม Supabase Auth กับ signup/login/logout/reset password ตาม SDK ปัจจุบัน
สร้าง profile เมื่อ signup ผ่าน flow ที่ไม่รับ role จากผู้สมัครและไม่ทำให้การสมัครล้มเหลวจากข้อมูล optional
แสดงสถานะ pending/active/revoked/expired จากแหล่งจริง ไม่ใช้ localStorage เป็นแหล่งสิทธิ์
จัด session restoration, loading state, expired session และ error ที่ไม่แสดงข้อมูลลับ
ใช้ route guard เพื่อ UX แต่คง enforcement ที่ DB/API
ไม่ cache สิทธิ์โดยไม่มีกติกา refresh เมื่อ revoke ผู้ใช้ต้องอ่าน content ใหม่ไม่ได้จาก backend แม้ UI ยังไม่อัปเดต
ตั้ง Site URL และ allowed redirects จากโค้ดจริง สร้าง docs/AUTH-SETUP.md รวม SMTP ข้อจำกัดและวิธีทดสอบ email ภายนอกทีม
ไม่ปิด email verification เพียงเพื่อซ่อนปัญหา SMTP สรุป choice และผลต่อ flow ให้ชัด
ไม่มี secret keys หรือ password ตัวอย่างที่ใช้จริงใน repo

ตรวจผล: สมัครและกู้คืนได้จริง รู้บัญชีแล้วตรวจสิทธิ์แยกทุกครั้ง


ขั้น 6: เชื่อมสมาชิกและหน้าเจ้าของ | P07 07 สร้างหน้า Admin จัดสิทธิ์ผ่านเว็บ
ใช้เมื่อ: หลัง Auth และ RPC ใช้งานได้

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล

งานรอบนี้:
สร้าง /admin/users, /admin/users/:id และ /admin/audit ให้เข้ากับ router เดิม
แสดงรายชื่อแบบ server pagination/search ไม่ดาวน์โหลด auth.users ทั้งหมดมา browser
ถ้าต้องค้น email ให้ทำผ่าน endpoint/RPC ที่ตรวจ admin และส่ง field จำเป็นเท่านั้น ไม่ grant ตาราง auth.users ให้ client และไม่ใส่ service_role ใน frontend
สมาชิกในรายการมีชื่อ สถานะสิทธิ์ แผน วันหมดอายุ และเวลาแก้ล่าสุด
หน้ารายคนมีเปิดสิทธิ์ ระงับสิทธิ์ ตั้งหมดอายุ พร้อม reason และ confirmation เมื่อเปลี่ยนสิทธิ์
ทุก action เรียก RPC/API ชุด 05 เท่านั้น ไม่ update ตารางตรงจาก browser
แสดง mutation pending, success, conflict, permission denied และ retry แบบ idempotent
หลังสำเร็จ refresh ข้อมูลจาก server ห้ามแสดงว่าสำเร็จก่อน response จริง
owner เท่านั้นจัด roles และป้องกันลด owner คนสุดท้าย อย่าเพิ่มปุ่ม impersonate หรือลบบัญชีถาวรในรุ่นแรก
UI รองรับมือถือ มี labels อ่านได้ ไม่สื่อสถานะด้วยสีอย่างเดียว
ทดสอบ unauthorized URL/direct API, admin concurrent edits และ audit

ตรวจผล: เจ้าของเปิด–ปิดสิทธิ์จากหน้าเว็บได้ สมาชิกเรียก action เดียวกันเองไม่ได้

ขั้น 7: นำสื่อเข้าระบบ | P09 09 สร้าง Private Storage และช่องทางไฟล์
ใช้เมื่อ: เลือก Supabase Storage หรือ R2 ตามไฟล์จริง

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้

กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
ตรวจชนิดและขนาด media ก่อนเลือก backend Storage
หากใช้ Supabase Storage ให้ private bucket และ policies ที่ตรวจ media entitlement และ publication status
หากใช้ R2 ให้ private bucket พร้อม endpoint/Worker ตรวจ session และ entitlement ก่อน streaming หรือสร้าง signed URL ห้ามให้ caller เลือก arbitrary object_path
แมป media_asset_id ไป object_path ที่ server อ่าน ไม่เชื่อ path จาก frontend
กำหนด signed URL อายุสั้นตาม UX อธิบายว่า revoke ไม่ยกเลิก URL ที่ออกแล้วทันที และข้อมูลที่โหลดแล้วเรียกคืนไม่ได้
validate upload ขนาด ชนิดไฟล์ และสิทธิ์ ไม่เชื่อ MIME ที่ client ส่งอย่างเดียว
cache private response อย่างปลอดภัย ไม่แชร์ผลของผู้ใช้ให้ผู้อื่น หลีกเลี่ยง cache entitlements จน revoke ไม่ทำงาน
ไม่เก็บ signed URL ถาวรใน DB เก็บ path/version/checksum
ทำ docs/STORAGE.md รวม backup objects และการย้าย backend โดยใช้ interface เท่าที่จำเป็น

ตรวจผล: ไฟล์เสียเงินไม่เปิด anonymous และไม่มี arbitrary path access

ใช้เมื่อ: ก่อน deploy หรือเปลี่ยน schema

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล
กติกา: ตรวจ repo และ schema เดิมก่อน ไม่เขียนทับงานเดิม ไม่เปลี่ยน production เอง ไม่ใช้ข้อมูลลูกค้าจริงในการทดสอบ ไม่วาง secrets ใน frontend ไม่อ้างว่ารองรับคนพร้อมกันเท่าไรจนกว่าจะวัดจริง ทำไฟล์จริงพร้อมคู่มือและการทดสอบที่สัมพันธ์กับความเสี่ยง ตรวจเอกสารทางการปัจจุบันก่อนใช้ API/CLI

งานรอบนี้:
ทำ access matrix และ meaningful tests บน local/test/staging:
anonymous อ่านได้เฉพาะ published free
pending/revoked/expired อ่าน paid content/assets ไม่ได้
active member อ่านตามสิทธิ์และ own attempts ได้
A อ่าน/แก้ B ไม่ได้ แม้รู้ ID
member เปลี่ยน role/entitlement/publication ไม่ได้
user_metadata role=admin ปลอมไม่มีผล
admin แก้สิทธิ์แล้ว audit ครบ และ transaction rollback หากขั้นหนึ่งผิด
สอง admin ใช้ expected_version เกิด conflict ที่จัดการได้
owner คนสุดท้ายลด role ไม่ได้ รวม concurrent cases
signed URL ขอบเขตถูกต้องและ expiry มีผล
import resume ไม่ซ้ำและ failed publish ไม่เปิดไฟล์ไม่ครบ
frontend build/typecheck และ end-to-end signup/admin approval/play/revoke/refresh/reset
ใช้ user sessions จริงหรือ test framework จำลอง role+JWT ตาม docs ไม่ใช้ service role ผ่านแล้วอ้างว่า member policies ถูกต้อง
แยกผล passed, failed, skipped และ prerequisites ที่ขาด ถ้าไม่มี credentials ให้เตรียม tests แต่บอกว่ายังไม่ได้ทดสอบจริง
ห้ามสร้างชุดทดสอบที่ mirror implementation อย่างเดียว

ตรวจผล: มีหลักฐานทดสอบ API และ policy ไม่ใช่แค่ภาพหน้าจอ


ขั้น 8: ทดสอบและนำเว็บขึ้นออนไลน์ | P13 13 Deploy, migrations และการกู้คืน
ใช้เมื่อ: เมื่อ staging ผ่านและเลือกปลายทางแล้ว

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้

งานรอบนี้:
สร้าง docs/DEPLOY-RUNBOOK.md บอกลำดับ schema/functions/frontend ที่ compatible กับเวอร์ชันเดิม
ทำ environment checklist สำหรับ Auth URLs, SMTP, secrets, private buckets, DNS/HTTPS และ production branch
ก่อน schema เสี่ยงให้ backup ตรวจ project ref และ review migration ห้าม db reset กับ production
ใช้ expand/contract เมื่อเปลี่ยน field เริ่มเพิ่ม field ใหม่ ปรับ code/backfill ตรวจผลก่อนเลิกลบ field เดิมในรอบถัดไป
ทำ smoke tests หลัง deploy ด้วยบัญชี A/B/Admin และ API direct access
แยก rollback frontend, migration forward-fix และ restore data/storage ห้ามอ้าง rollback UI ย้อน DB ด้วย
ทำ backup inventory และ restore drill บน test project ระบุข้อมูลย้อนหลังที่ยอมสูญเสีย (RPO) และเวลาที่ต้องการกู้ (RTO) ที่ตกลงกับลูกค้า ไม่แต่ง SLA
เพิ่ม spending alerts และ quota monitoring พร้อมผู้รับผิดชอบ แยก alert จาก hard caps
ยังไม่ push/deploy ไป production หรือเรียก migration remote จนผมระบุปลายทางและยืนยัน operation ที่จะทำ

ตรวจผล: มี runbook ที่เจ้าของทำซ้ำและรับช่วงดูแลได้


ขั้น 10: เปิดขายและดูแลต่อ | P14 14 สรุปส่งมอบและเช็กลิสต์
ใช้เมื่อ: หลังทุกส่วนสร้างและทดสอบแล้ว

บริบท: Web App ขายสื่อ interactive ประมาณ 1,000 รายการ รับโอนเงินนอกระบบ ผู้ปกครองสมัครบัญชี เจ้าของเปิดสิทธิ์ผ่านเว็บ ช่วงแรกผู้มีสิทธิ์เข้าใช้สื่อทั้งหมด โค้ดสร้างจาก AI และต้องตรวจ framework จริงก่อนแก้
แนวทาง: ใช้ Supabase Auth + PostgreSQL + private storage ตั้งต้น ใช้ hosting ให้ตรงโค้ดเดิม แยก frontend, API/data access และ database migrations ไม่เพิ่ม VPS หรือ microservices หากไม่มีเหตุผล

งานรอบนี้:
ทำ HANDOVER.md สำหรับมือใหม่ อธิบายคำศัพท์และขั้นตอนใช้ Admin เปิดสิทธิ์ ตั้ง expiry ระงับ และดู audit
สรุปไฟล์หลัก ตาราง/functions/policies และวิธีเพิ่ม media kind หรือ plan ในอนาคต
ใส่เช็กลิสต์พร้อมสถานะและ evidence: schema migrations, RLS/grants, RPC authorization, profiles bootstrap, Auth/email, Admin mutations, private storage, import resume, indexes/pagination, error handling, security tests, deploy smoke test, backup restore, budget alerts และ ownership

คำสั่งในเครื่อง (เลือกใช้ตามเงื่อนไข ไม่รันทั้งหมดต่อกัน)

ขั้น 4: เปิดเว็บบนเครื่องที่มีโปรเจกต์อยู่แล้ว
ต้องอยู่ในโฟลเดอร์โปรเจกต์ที่มี package.json และ package-lock.json; ใช้คำสั่งให้ตรง scripts ของโค้ด
npm ci
npm run dev

ขั้น 4: ตรวจไฟล์พร้อมใช้บนเครื่อง
หยุด dev ด้วย Ctrl+C เมื่อจำเป็น จากนั้นตรวจไฟล์ที่ build แล้ว; preview ยังไม่ใช่เว็บขายจริง
npm run build
npm run preview

ขั้น 5: เตรียมเครื่องมือ Supabase
ใช้เมื่อเลือก workflow ผ่าน CLI และติดตั้ง runtime ที่เอกสารกำหนดแล้ว เช่น Docker สำหรับฐานข้อมูล local
npm install --save-dev supabase
npx supabase --help
npx supabase init
npx supabase start

ขั้น 5: สร้างคำสั่งเปลี่ยนตาราง
สร้างไฟล์แล้วให้ Codex เติม SQL และ review ก่อน ไม่ใช่สร้างตารางเสร็จทันที
npx supabase migration new create_worksheet_schema

ขั้น 5: ทดลองฐานข้อมูลบนเครื่อง
ล้างข้อมูลได้ ใช้เฉพาะฐาน local ที่ทิ้งข้อมูลได้ ห้ามเติม --linked หรือ --db-url เพื่อชี้ฐานขายจริง ตรวจและสร้างโฟลเดอร์ src/types ก่อนสร้างไฟล์ types
npx supabase db reset
npx supabase gen types typescript --local > src/types/database.generated.ts

ขั้น 5: เชื่อมโครงการทดลองบน Supabase
แทน YOUR_TEST_PROJECT_REF ด้วยรหัสโครงการทดลองจริง ตรวจชื่อและเป้าหมายก่อนทุกครั้ง หากเป็นฐานเดิมให้ผู้พัฒนาทบทวนการดึง schema ก่อน
npx supabase login
npx supabase link --project-ref YOUR_TEST_PROJECT_REF
npx supabase migration list
npx supabase db push --dry-run

ขั้น 5: ส่งคำสั่งตารางไปโครงการทดลอง
ทำหลังอ่านผล dry-run และยืนยันว่า linked ไป TEST/STAGING เท่านั้น ถ้าเป็นฐานจริงให้ใช้แผนสำรองและแผนปล่อยเวอร์ชันในขั้น 8
npx supabase db push
npx supabase gen types typescript --linked > src/types/database.generated.ts

ขั้น 6: ทางเลือก: ฟังก์ชันจัดการสิทธิ์
ใช้เฉพาะเมื่อโครงสร้างเลือกใช้ Supabase Edge Function ไม่จำเป็นทุกโปรเจกต์ คำสั่ง serve เป็นการทดสอบบนเครื่อง
npx supabase functions new admin-access
npx supabase functions serve admin-access

ขั้น 8: ทางเลือก: ส่งฟังก์ชันขึ้นบริการ
ใช้เมื่อมีฟังก์ชันนี้จริงและตรวจบัญชี เป้าหมาย สิทธิ์ และค่าตั้งแล้ว ปล่อยตามแผนพร้อมสำรอง ห้ามส่งขึ้นฐานขายจริงโดยเดาเป้าหมาย
npx supabase functions deploy admin-access
