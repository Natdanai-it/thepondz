ฉบับ 2026-10-11-R2 • เอกสารเสริมสำหรับผู้พัฒนา

รายการตรวจเชิงเทคนิคสำหรับผู้พัฒนา
ตั้งแต่โค้ดบนเครื่องจนเปิดขาย

70 ข้อสำหรับผู้พัฒนา จัดตามขั้น 1–10 • ลูกค้าใช้เช็กลิสต์หลัก 12 ข้อ

ติ๊กเมื่อมีหลักฐานว่าตรวจแล้ว ช่องที่ยังไม่ผ่านให้จดงานคงค้าง รายการนี้เป็นแนวทางสำหรับเว็บสมาชิกและสื่อ interactive ไม่ใช่การรับรองว่าระบบปลอดภัยหรือไม่มีวันล่ม

สถานะเก็บเฉพาะ browser เครื่องนี้ ไม่ซิงก์กับลูกค้าหรือระบบจริง ห้ามใส่รหัสผ่าน กุญแจลับ หรือข้อมูลสมาชิกในบันทึก

ขั้น 1: กำหนดสิ่งที่จะขาย

ตรวจอย่างไร: ระบุถาวร/หมดอายุ สื่อใหม่รวมไหม และบัญชีใช้กี่เครื่อง

ทำไมสำคัญ: ลดการเปลี่ยน schema และความเข้าใจผิดหลังขาย

ตรวจอย่างไร: เริ่มบัญชีผู้ปกครอง ไม่เก็บชื่อจริง/วันเกิดเด็กโดยไม่มีเหตุผล

ทำไมสำคัญ: ลดข้อมูลส่วนตัวที่ต้องดูแลและแยกสิ่งจำเป็นจากสิ่งอยากได้

กลับขั้น 1 ในคอร์สหลัก

ขั้น 2: เลือกบริการและวางงบ

ตรวจอย่างไร: เปิด package.json, README และดูว่ามี server code หรือไม่

ทำไมสำคัญ: เลือก static hosting, serverless หรือ backend server ให้ตรงโค้ด

ตรวจอย่างไร: จด storage, bandwidth, requests และ pause/sleep

ทำไมสำคัญ: โควตาฟรีบางบริการหยุด บางบริการคิดเพิ่ม

ตรวจอย่างไร: อ่าน commercial use และเงื่อนไขล่าสุด

ทำไมสำคัญ: Vercel Hobby จำกัดงานส่วนตัวไม่ใช่เชิงพาณิชย์

กลับขั้น 2 ในคอร์สหลัก

ขั้น 3: เตรียมบัญชีและเครื่องมือ

ตรวจอย่างไร: ตรวจเจ้าของ repo, Cloud, domain และ billing

ทำไมสำคัญ: ส่งต่องานและต่ออายุได้โดยไม่พึ่งบัญชีผู้สอน

ตรวจอย่างไร: ตรวจ commit ที่จะ deploy และ dependency versions

ทำไมสำคัญ: ทำซ้ำและย้อนโค้ดได้ ลดความต่างระหว่างเครื่อง

ตรวจอย่างไร: ตั้งผ่านบัญชีเจ้าของและเก็บในที่ปลอดภัย

ทำไมสำคัญ: ป้องกันบัญชีหลักและช่วยกู้การเข้าถึง

ตรวจอย่างไร: ตรวจ .env และไฟล์ที่ track รวมประวัติที่เคยเผยแพร่

ทำไมสำคัญ: ถ้าเคยหลุดต้อง revoke/rotate การลบไฟล์ล่าสุดอย่างเดียวไม่พอ

ตรวจอย่างไร: ตรวจ VITE_* และไฟล์ผล build

ทำไมสำคัญ: ค่าฝังใน browser ถือว่าผู้ใช้เห็นได้

ตรวจอย่างไร: ตรวจ URLs และชื่อ env ตามโค้ด ห้ามแสดง secrets ในภาพสอน

ทำไมสำคัญ: ค่าบางชนิดต้อง rebuild จึงเปลี่ยนผล frontend

ตรวจอย่างไร: ใช้ project หรือข้อมูลทดสอบแยก พร้อม env ที่ถูกชุด

ทำไมสำคัญ: ไม่ทดสอบ import หรือลบข้อมูลบนลูกค้าจริง

กลับขั้น 3 ในคอร์สหลัก

ขั้น 4: สร้างและลองหน้าเว็บ

ตรวจอย่างไร: เปิดหน้าและเล่นกิจกรรมตัวอย่างด้วยบัญชีทดสอบ

ทำไมสำคัญ: แก้ปัญหาที่ local ก่อนส่งขึ้น Cloud

ตรวจอย่างไร: รัน build ตาม scripts จริงและอ่าน logs

ทำไมสำคัญ: dev ผ่านไม่ได้รับรอง production build

ตรวจอย่างไร: ตรวจว่าไฟล์ deploy อยู่ dist หรือ directory ใด

ทำไมสำคัญ: อัปโหลด source ผิดชุดอาจทำให้หน้าไม่ขึ้น

กลับขั้น 4 ในคอร์สหลัก

ขั้น 5: สร้างฐานข้อมูลและกฎสิทธิ์

ตรวจอย่างไร: ตรวจ RLS และ grants ของตารางที่เปิด API

ทำไมสำคัญ: public key ใช้งานได้เมื่อกฎข้อมูลถูกต้อง

ตรวจอย่างไร: ตรวจ read/write/update/delete ของแต่ละตาราง

ทำไมสำคัญ: ซ่อนปุ่มหรือ route guard อย่างเดียวไม่พอ

ตรวจอย่างไร: อ่านชื่อ column ชนิดข้อมูล FK และ deletion behavior

ทำไมสำคัญ: รู้ผลกระทบเมื่อแก้หรือลบข้อมูล

ตรวจอย่างไร: ทดสอบข้อมูลผิด FK, duplicate slug และ duplicate entitlement

ทำไมสำคัญ: ป้องกันข้อมูลเสียก่อนกระทบหน้าเว็บ

ตรวจอย่างไร: apply บนฐานทดสอบว่างและ schema เดิม

ทำไมสำคัญ: ไม่ใช่แค่สร้างจากศูนย์แล้วอ้าง upgrade ได้

ตรวจอย่างไร: ตรวจ PUBLIC, anon, authenticated และ role ผู้ใช้จริง

ทำไมสำคัญ: RLS และ execute grants ต้องทำงานร่วมกัน

ตรวจอย่างไร: ตั้ง expires_at ในอดีตแล้วเรียก paid API

ทำไมสำคัญ: ไม่รอ cron หรือเชื่อเวลา browser

ตรวจอย่างไร: ทดสอบ member calling RPC และ function search_path

ทำไมสำคัญ: function พิเศษไม่เป็นช่องยกระดับสิทธิ์

กลับขั้น 5 ในคอร์สหลัก

ขั้น 6: เชื่อมสมาชิกและหน้าเจ้าของ

ตรวจอย่างไร: สร้างบัญชีใหม่แล้วลองเปิดกิจกรรมและเรียก API ตรง

ทำไมสำคัญ: login กับสิทธิ์ซื้อเป็นคนละขั้น

ตรวจอย่างไร: ใช้บัญชีปกติลองเรียกคำสั่งเปิดสิทธิ์

ทำไมสำคัญ: สมาชิกต้องไม่แก้สิทธิ์หรือ role ของตัวเองได้

ตรวจอย่างไร: ทดสอบผ่าน API ด้วย session A

ทำไมสำคัญ: ผู้ซื้อสื่อไม่ได้รับสิทธิ์อ่านผลส่วนตัวของคนอื่น

ตรวจอย่างไร: ตรวจ admin_id, user_id, เวลา และการเปลี่ยนแปลง

ทำไมสำคัญ: ช่วยตรวจปัญหาและความผิดพลาดของผู้ดูแล

ตรวจอย่างไร: ใช้บัญชีนอกทีมทดสอบ inbox/spam และลิงก์

ทำไมสำคัญ: Supabase default SMTP จำกัดทีม ต้องต่อบริการส่งจริงเมื่อใช้ Auth email

ตรวจอย่างไร: ตรวจ user_roles กับ entitlements แยกกัน

ทำไมสำคัญ: ผู้ซื้อไม่กลายเป็นผู้ดูแล

ตรวจอย่างไร: จำลอง failure และตรวจ rollback

ทำไมสำคัญ: ไม่เกิดเปิดสิทธิ์แต่ไม่มีประวัติ

ตรวจอย่างไร: ทดลองลด owner รวม concurrent cases บน test

ทำไมสำคัญ: ไม่ทำให้ระบบขาดผู้ดูแลสูงสุด

ตรวจอย่างไร: ใช้ member ลอง endpoint รายชื่อและตรวจ fields

ทำไมสำคัญ: ไม่เปิดข้อมูลสมาชิกทั้งหมดให้ browser ปกติ

ตรวจอย่างไร: เปิดสิทธิ์แล้ว revoke/ตั้งหมดอายุ ทดสอบ request ใหม่

ทำไมสำคัญ: ตรวจเวลา expiry ฝั่งฐานข้อมูลหรือ server

ตรวจอย่างไร: ส่ง user_metadata role=admin แล้วเรียก action

ทำไมสำคัญ: ไม่เชื่อข้อมูลที่สมาชิกแก้เอง

ตรวจอย่างไร: ส่ง request_id/submission_key เดิมสองครั้ง

ทำไมสำคัญ: retry ไม่สร้างสิทธิ์หรือคะแนนซ้ำ

ตรวจอย่างไร: ใช้สอง admin กับ expected_version เดียวกัน

ทำไมสำคัญ: ป้องกันเขียนทับเงียบ

ตรวจอย่างไร: จำลอง request fail แล้วดูสถานะหน้า Admin

ทำไมสำคัญ: ไม่แจ้งเปิดสิทธิ์สำเร็จทั้งที่ DB ไม่เปลี่ยน

ขั้น 7: นำสื่อเข้าระบบ

ตรวจอย่างไร: generate types แล้วตรวจ renderer ของ payload แต่ละ version

ทำไมสำคัญ: เพิ่มสื่อชนิดใหม่โดยไม่ทำรุ่นเดิมพัง

ตรวจอย่างไร: ดู query plan/latency staging และขนาด response

ทำไมสำคัญ: ลด full scan, N+1 และการโหลดข้อมูลเกิน

ตรวจอย่างไร: ทดสอบ A/B และ revoke เมื่อ cache เปิด

ทำไมสำคัญ: ไม่ส่งข้อมูลผู้ใช้หรือ paid payload ข้ามบัญชี

ตรวจอย่างไร: รวม GB และดูขนาดใหญ่สุด พร้อมจำนวนภาพและเสียง

ตรวจอย่างไร: ลองเปิด object URL โดยไม่ login และตรวจ policy

ทำไมสำคัญ: URL สาธารณะอาจข้ามการตรวจสิทธิ์ในหน้าเว็บ

ตรวจอย่างไร: ทดลอง 10 รายการและ retry รายการผิด

ทำไมสำคัญ: ไม่อัปโหลดซ้ำหรือสร้างแถวซ้ำเมื่อทำต่อ

ตรวจอย่างไร: ตรวจ manifest และไฟล์ที่อ้างอิงทั้งหมด

ทำไมสำคัญ: หลีกเลี่ยงรายการที่แสดงแต่เล่นไม่ได้

ตรวจอย่างไร: ตรวจ Network ว่าเปิดหน้ารวมไม่โหลดทั้ง 1,000 สื่อ

ทำไมสำคัญ: ลดความช้าและค่าดาวน์โหลด

ตรวจอย่างไร: หากมีโค้ด ให้ตรวจ sandbox/origin และการส่งข้อความ

ทำไมสำคัญ: โค้ดกิจกรรมต้องไม่เข้าถึง session หลักโดยไม่จำเป็น

ตรวจอย่างไร: เปิดบนมือถือจริงหลังบีบอัดภาพ/เสียง

ทำไมสำคัญ: ไฟล์เล็กช่วยโหลด แต่ต้องไม่ลดคุณภาพจนเด็กใช้ไม่ได้

ตรวจอย่างไร: จำลอง upload สำเร็จแต่ DB fail และกลับกัน

ทำไมสำคัญ: แก้ orphan files/rows โดยไม่ publish สื่อไม่ครบ

ตรวจอย่างไร: ตรวจ signed URL expiry และพฤติกรรมหลัง revoke

ทำไมสำคัญ: URL อาจใช้ได้จนหมดอายุ ไฟล์ที่โหลดไปแล้วเรียกคืนไม่ได้

ตรวจอย่างไร: เรียก catalog เป็น anonymous แล้วตรวจไม่มี paid content

ทำไมสำคัญ: ภาพรายการฟรีไม่เผยเนื้อหาที่ขาย

ตรวจอย่างไร: ทดลองงาน import เกินหนึ่ง request แล้ว resume

ทำไมสำคัญ: ไม่ค้างเพราะ timeout request
