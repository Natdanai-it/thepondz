เลือกเส้นทางเรียน: เครื่องมือง่าย → เว็บ → แอปข้อมูลจริง

เป้าหมายคือให้คุณสามารถเอา “ไอเดีย” ไปคุยกับ AI แล้วค่อย ๆ ได้เว็บหรือแอปที่ดูดี ใช้งานง่าย และแก้ต่อได้ โดยไม่ต้องเริ่มจากการเขียนโค้ดเอง

0–15 นาทีเข้าใจวิธีสั่ง AI และคำศัพท์ที่ต้องรู้
15–35 นาทีเปลี่ยนไอเดียให้เป็นสิ่งที่ AI เข้าใจ
35–55 นาทีวางหน้าเว็บและกำหนดหน้าตา
55–80 นาทีสั่งสร้างเว็บจริงทีละส่วน
80–100 นาทีสั่งแก้ให้สวยขึ้น + รองรับมือถือ
100–115 นาทีWeb App + ฟอร์ม + Dashboard + สถานะ
115–120 นาทีPrompt ชุดกลับบ้าน
เลือกเส้นทางที่ตรงกับพื้นฐานของคุณ

เส้นทางเริ่มง่าย: Forms + Sheets, Apps Script, Notion, GitHub Pages และเครื่องมือ No-code เลือกทำหนึ่งชิ้นงานก่อน

เส้นทาง Prompt + UI: ใช้ตารางเวลา 2 ชั่วโมงด้านบนเป็นแนวฝึกพื้นฐาน อธิบายโจทย์ ออกแบบหน้าเว็บ และแก้หน้าตาทีละรอบ

เส้นทาง Web App + Database: ต่อ Auth/RLS และ Hosting เมื่อพร้อมฝึกข้อมูลจริง บทฝึกต่อใช้เวลาตามพื้นฐานและเครื่องมือที่เลือก ไม่จำเป็นต้องทำทุก Lab จบในคาบเดียว

แบบที่ชัดกว่า

“สร้างเว็บบริษัท IT โทนขาว-น้ำเงิน ดูมืออาชีพ หน้าแรกต้องเห็นบริการ ผลงาน และปุ่มติดต่อทันที รองรับมือถือ และไม่เอาแสง Glow”

AI รู้ทั้งเป้าหมาย หน้าตา และข้อห้าม
Prompt 01ให้ AI ถามเราก่อนเริ่มทำ
ฉันอยากสร้างเว็บไซต์ แต่รายละเอียดอาจยังไม่ครบ

ก่อนเขียนโค้ด ช่วยถามฉันทีละข้อเฉพาะเรื่องที่จำเป็น:
1. เว็บนี้ทำขึ้นเพื่ออะไร
2. ใครเป็นคนใช้
3. ต้องมีหน้าอะไรบ้าง
4. ต้องมีข้อมูลอะไร
5. อยากได้หน้าตาประมาณไหน
6. มีเว็บตัวอย่างที่ชอบไหม
7. ต้องรองรับมือถือหรือไม่
8. มีอะไรที่ไม่ต้องการให้ทำ

หลังจากฉันตอบครบแล้ว ให้สรุปสิ่งที่ฉันต้องการเป็นภาษาง่าย ๆ
ยังไม่ต้องเขียนโค้ด
เหมาะมากสำหรับคนที่ยังไม่รู้ว่าจะเริ่มอธิบายระบบจากตรงไหน

Prompt 02ตัวอย่าง Prompt สำหรับเว็บ Portfolio
ช่วยสร้างเว็บไซต์ Portfolio สำหรับคนรับงาน IT

เป้าหมาย:
ให้คนที่เข้ามารู้ภายในไม่กี่วินาทีว่าฉันรับทำอะไร และสามารถดูผลงานหรือกดติดต่อได้ง่าย

คนที่เข้ามาดู:
- คนที่ต้องการ IT Support
- ธุรกิจที่ต้องการเว็บไซต์หรือระบบ
- คนที่สนใจเรียนคอมพิวเตอร์แบบตัวต่อตัว

ข้อมูลที่ต้องมี:
- แนะนำตัวสั้น ๆ
- บริการ
- คอร์ส
- โปรเจกต์ที่เคยทำ
- รีวิว
- ราคาเริ่มต้น
- ช่องทางติดต่อ

หน้าตา:
- ทันสมัย
- ดูเป็นมืออาชีพ
- พื้นหลังสว่าง
- ใช้รูปประกอบที่เกี่ยวข้องจริง
- ตัวหนังสืออ่านง่าย

การจัดหน้า:
หน้าแรก → บริการ → ผลงาน → คอร์ส → รีวิว → ราคา → ติดต่อ

การใช้งาน:
คนต้องกดไปดู “ผลงาน / คอร์ส / ติดต่อ” ได้ง่าย

มือถือ:
ต้องออกแบบใหม่ให้เหมาะกับมือถือ ไม่ใช่แค่ย่อหน้า Desktop

ไม่ต้องการ:
- แสง Glow
- Neon
- Gradient เยอะ
- การ์ดซ้ำ ๆ ทุก Section
- ช่องว่างยาวเกินไป
- Animation ที่รบกวนการอ่าน

จากไอเดียสู่ระบบ

เปลี่ยนประโยคสั้น ๆ ให้ AI เข้าใจงานจริง

แทนที่จะบอกแค่ชื่อระบบ ให้ตอบ 4 คำถาม: “ใครใช้ / ทำอะไร / เก็บอะไร / เสร็จแล้วเห็นอะไร”

ไอเดียเดิม“อยากได้ระบบแจ้งซ่อม”
→
อธิบายให้ชัดขึ้นพนักงานแจ้งปัญหา → ช่างรับงาน → เปลี่ยนสถานะ → ผู้แจ้งกลับมาดูได้
Prompt 03แปลงไอเดียให้เป็นแผนระบบ
ฉันอยากทำ “ระบบแจ้งซ่อม”

คนที่ใช้:
- พนักงาน: แจ้งปัญหาและดูสถานะ
- ช่าง: ดูงานที่ได้รับและอัปเดตสถานะ
- Admin: ดูงานทั้งหมดและจัดการประเภทปัญหา

ข้อมูลที่ต้องเก็บ:
- หัวข้อ
- รายละเอียด
- รูปภาพ
- ผู้แจ้ง
- วันที่
- ผู้รับผิดชอบ
- สถานะ

ช่วยฉัน:
1. สรุปว่าระบบนี้ต้องมีอะไรบ้าง
2. แบ่งเป็น “จำเป็นตอนแรก” กับ “ทำเพิ่มทีหลัง”
3. เสนอหน้าที่ต้องมี
4. เสนอเส้นทางการใช้งานแบบง่าย
5. บอกข้อมูลที่ฉันยังไม่ได้ระบุ

ให้ AI บอกก่อนว่า Section ไหนควรใช้ภาพจริง ภาพหน้าจอ หรือภาพประกอบ แล้วค่อยใส่ลงเว็บ

ภาพจริงเหมาะกับบริการ / คน / ผลงานจริง
ภาพหน้าจอเหมาะกับเว็บ / Dashboard / ระบบ
ภาพประกอบเหมาะกับเรื่องที่อธิบายด้วยภาพง่ายกว่า

3. รูปควรสื่ออะไร
4. ควรวางซ้าย/ขวา/เต็มความกว้าง
5. มือถือควรแสดงรูปอย่างไร

11
Website vs Web App

เว็บแนะนำบริการกับระบบใช้งานจริง สั่ง AI ไม่เหมือนกัน

Website เน้นให้คนอ่านและตัดสินใจ ส่วน Web App เน้นให้คนทำงาน เช่น กรอกฟอร์ม อนุมัติ ค้นหา และดูสถานะ

Prompt 10Prompt สำหรับ Web App
ช่วยออกแบบ Web App สำหรับระบบคำขอภายในบริษัท

ผู้ใช้:
- พนักงาน: สร้างคำขอและดูสถานะ
- หัวหน้า: อนุมัติหรือปฏิเสธ
- Admin: ดูทั้งหมดและตั้งค่าระบบ

งานหลัก:
- กรอกคำขอ
- แนบไฟล์
- ดูสถานะ
- อนุมัติ / ปฏิเสธ
- ค้นหาและกรองรายการ

ขอให้เน้น “ใช้งานง่าย” มากกว่าตกแต่ง
ทุกหน้าต้องบอกให้ผู้ใช้รู้ว่าต้องทำอะไรต่อ

ช่วยออกแบบ:
- หน้า Dashboard
- ฟอร์มสร้างคำขอ
- หน้ารายละเอียด
- หน้ารออนุมัติ
- หน้าจัดการของ Admin

และต้องมีสถานะ:
กำลังโหลด / ไม่มีข้อมูล / สำเร็จ / ผิดพลาด / ปุ่มกดไม่ได้ / ยืนยันก่อนลบ
12
หน้าจอต้องบอกสถานะ

ระบบที่ดู “ครบ” ต้องคิดตอนที่ยังไม่มีข้อมูลและตอนที่เกิดปัญหาด้วย

มือใหม่มักออกแบบเฉพาะตอนทุกอย่างทำงานปกติ แต่ผู้ใช้จริงจะเจอ Loading, Error และข้อมูลว่างแน่นอน

กำลังโหลดบอกว่าระบบกำลังทำงาน
ยังไม่มีข้อมูลบอกว่าต้องเริ่มจากอะไร
สำเร็จยืนยันว่าบันทึกแล้ว
ผิดพลาดบอกสาเหตุและวิธีลองใหม่
กดไม่ได้ปิดปุ่มเมื่อข้อมูลยังไม่ครบ
ยืนยันก่อนทำเช่น ลบข้อมูลหรืออนุมัติรายการ
Prompt 11ให้ AI เติมสถานะที่ขาด
ตรวจ Web App นี้ว่ามีหน้าจอรองรับสถานการณ์เหล่านี้ครบหรือยัง:
- กำลังโหลด
- ไม่มีข้อมูล
- บันทึกสำเร็จ
- เกิดข้อผิดพลาด
- ไม่มีสิทธิ์
- ปุ่มยังไม่สามารถกดได้
- ยืนยันก่อนลบหรือทำรายการสำคัญ

ถ้ายังขาด ให้เพิ่มข้อความและหน้าตาที่เข้าใจง่าย
อย่าเพิ่ม Animation ที่ไม่จำเป็น

function doGet() {
  return HtmlService.createHtmlOutputFromFile('Index')
    .setTitle('แบบฝึกรับแจ้งปัญหา');

function sheet_() {
  const id = PropertiesService.getScriptProperties().getProperty('SPREADSHEET_ID');
  if (!id) throw new Error('ยังไม่ได้ตั้ง SPREADSHEET_ID ใน Script properties');
  const sheet = SpreadsheetApp.openById(id).getSheetByName('Requests');
  if (!sheet) throw new Error('ไม่พบแท็บ Requests');
  const expected = ['id', 'created_at', 'title', 'category', 'status'];
  const header = sheet.getRange(1, 1, 1, expected.length).getValues()[0];
  if (expected.some((name, i) => header[i] !== name)) {
    throw new Error('หัวคอลัมน์ Requests ไม่ตรงตัวอย่าง กรุณาตรวจแถว 1');
  }
  return sheet;
}

function saveRequest(input) {
  if (!input || typeof input.title !== 'string' || typeof input.category !== 'string') {
    throw new Error('ข้อมูลไม่ครบ');
  }
  const title = input.title.trim();
  const categories = ['Hardware', 'Software', 'Network', 'Other'];
  if ([...title].length < 3 || [...title].length > 120) {
    throw new Error('หัวข้อต้องมี 3–120 ตัวอักษร');
  }
  if (!categories.includes(input.category)) throw new Error('ประเภทไม่ถูกต้อง');
  // ข้อความผู้ใช้ต้องไม่ถูก Sheets ตีความเป็นสูตร
  const safeTitle = /^[=+@-]/.test(title) ? "'" + title : title;
  const lock = LockService.getScriptLock();
  lock.waitLock(10000);
  try {
    const id = Utilities.getUuid();
    sheet_().appendRow([id, new Date(), safeTitle, input.category, 'new']);
    SpreadsheetApp.flush();
    return { id: id, message: 'บันทึกแล้ว' };
  } finally {
    lock.releaseLock();
  }
}

localStorage ไม่ใช่ฐานข้อมูลกลาง: เก็บใน Browser ของเครื่องนั้น เหมาะกับค่าหน้าจอหรือเดโม ไม่ใช่หลักฐานว่าระบบบันทึกให้ลูกค้าทุกคนแล้ว ข้อมูลจำลองต้องติดป้ายว่า “ข้อมูลตัวอย่าง” และไม่แจ้งว่าส่งสำเร็จก่อนบริการตอบรับ

ทำไม Browser ติดต่อ Supabase ได้ ทั้งที่บอกว่าต้องมี Backend?

Supabase มีส่วน Backend จัดการให้แล้ว Browser เรียก API ผ่าน HTTPS ไม่ได้ถือรหัสผ่าน PostgreSQL โดยตรง กุญแจ publishable ระบุโปรเจกต์ ส่วน token และ RLS ตัดสินสิทธิ์ งานที่ใช้กุญแจลับ เช่น เรียก AI แบบคิดเงิน ต้องผ่าน Backend ที่เราเขียนเพิ่ม

-- ถ้ามีตารางนี้แล้ว ให้ตรวจ schema และทำ migration แทนการรันทับ
begin;

create table public.service_requests (
  id uuid primary key default gen_random_uuid(),
  owner_id uuid not null default auth.uid()
    references auth.users(id) on delete cascade,
  title text not null check (char_length(btrim(title)) between 3 and 120),
  description text not null default '' check (char_length(description) <= 2000),
  status text not null default 'new'
    check (status in ('new', 'in_progress', 'done')),
  created_at timestamptz not null default now()
);

create index service_requests_owner_created_idx
  on public.service_requests (owner_id, created_at desc);

alter table public.service_requests enable row level security;
revoke all on public.service_requests from anon;
grant select, insert, update, delete on public.service_requests to authenticated;

create policy "Read own requests" on public.service_requests
  for select to authenticated using ((select auth.uid()) = owner_id);

create policy "Create own requests" on public.service_requests
  for insert to authenticated with check ((select auth.uid()) = owner_id);

create policy "Update own requests" on public.service_requests
  for update to authenticated
  using ((select auth.uid()) = owner_id)
  with check ((select auth.uid()) = owner_id);

create policy "Delete own requests" on public.service_requests
  for delete to authenticated using ((select auth.uid()) = owner_id);

commit;

// src/lib/supabase.js — React/Vite, @supabase/supabase-js
import { createClient } from '@supabase/supabase-js';

const url = import.meta.env.VITE_SUPABASE_URL;
const publishableKey = import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY;
if (!url || !publishableKey) {
  throw new Error('ยังไม่ได้ตั้งค่า Supabase URL / publishable key');
}
export const supabase = createClient(url, publishableKey);

export async function loadRequests() {
  const { data: identity, error: authError } = await supabase.auth.getUser();
  if (authError || !identity.user) throw new Error('กรุณาเข้าสู่ระบบ');
  const { data, error } = await supabase
    .from('service_requests')
    .select('id, title, description, status, created_at')
    .order('created_at', { ascending: false });
  if (error) throw error;
  return data; // RLS กรองเจ้าของ ไม่พึ่งการซ่อนแถวในหน้าจอ
}

export async function createRequest(title, description) {
  const { data: identity, error: authError } = await supabase.auth.getUser();
  if (authError || !identity.user) throw new Error('กรุณาเข้าสู่ระบบ');
  const cleanTitle = title.trim();
  if ([...cleanTitle].length < 3 || [...cleanTitle].length > 120) {
    throw new Error('หัวข้อต้องยาว 3–120 ตัวอักษร');
  }
  if ([...description].length > 2000) throw new Error('รายละเอียดไม่เกิน 2,000 ตัวอักษร');
  const { data, error } = await supabase
    .from('service_requests')
    .insert({ owner_id: identity.user.id, title: cleanTitle, description, status: 'new' })
    .select('id, title, description, status, created_at')
    .single();
  if (error) throw error;
  return data; // แสดงสำเร็จหลังถึงบรรทัดนี้เท่านั้น
}
